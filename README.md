# AI Storefront Generator

A mobile-first SuperProfile take-home: turn a creator description into an AI-written bio and 2–4 offers with INR prices, edit or regenerate the draft, then publish a shareable storefront.

**Stack:** React, TypeScript, Vite and Tailwind on Cloudflare Pages; Convex database and HTTP actions; Kilo AI Gateway. No login, scraping, checkout, or contact collection.

## Run locally

Requires Node 22.18+ (Node 24 recommended), npm, and a Convex account. Docker and Postgres are no longer required.

```sh
npm ci
npx convex login
npx convex dev
```

Choose your existing development project. The CLI generates `convex/_generated/` bindings and writes deployment configuration to the ignored `.env.local`. For this project's development deployment:

```dotenv
CONVEX_DEPLOYMENT=dev:bold-bandicoot-351
VITE_CONVEX_URL=https://bold-bandicoot-351.convex.cloud
```

Configure server settings in Convex:

```sh
cp convex/.env.example .env.convex.local
openssl rand -hex 32
# Put the generated value in RATE_LIMIT_SALT and configure your Kilo key.
npx convex env set --from-file .env.convex.local
```

In another terminal:

```sh
npm run dev
```

Open **http://127.0.0.1:5173**. Set `APP_ORIGIN` in Convex to this exact origin for local development. For a fresh project, use the URL generated for your own deployment. `npm run dev:backend` keeps backend code synchronized; `npx convex dev --once` pushes one development update.

## Configuration

Browser values belong in Vite environment files or Cloudflare build settings. Server values belong in Convex environment variables; `.env.convex.local` is only an ignored local input file for the CLI.

| Variable                                                 | Location          | Purpose                                                                                         |
| -------------------------------------------------------- | ----------------- | ----------------------------------------------------------------------------------------------- |
| `VITE_CONVEX_URL`                                        | Browser           | Deployment URL ending in `.convex.cloud`. The app derives its `.convex.site/api` HTTP endpoint. |
| `VITE_API_URL`                                           | Browser, optional | Full HTTP API override; normally leave unset.                                                   |
| `VITE_POSTHOG_KEY`, `VITE_POSTHOG_HOST`                  | Browser, optional | Blank key disables analytics delivery.                                                          |
| `CONVEX_DEPLOYMENT`                                      | CLI               | Selects the development deployment; generated by `convex dev`.                                  |
| `APP_ORIGIN`                                             | Convex server     | Exact allowed frontend origin, without a trailing slash.                                        |
| `RATE_LIMIT_SALT`                                        | Convex server     | Required random secret for hashing rate-limit keys.                                             |
| `KILO_API_KEY`                                           | Convex server     | Optional Kilo credential; blank uses shared anonymous access.                                   |
| `KILO_MODELS`, `KILO_JSON_MODELS`                        | Convex server     | Ordered free model IDs and the subset supporting strict JSON schemas.                           |
| `KILO_DISABLE_REASONING`, `KILO_MAX_TOKENS`              | Convex server     | Defaults: `true`, `3000`.                                                                       |
| `IP_GENERATIONS_PER_HOUR`, `GLOBAL_DAILY_GENERATION_CAP` | Convex server     | Defaults: `10`, `100`, shared across generation and regeneration.                               |

Never put provider or Convex deploy credentials in `VITE_` variables. Rebuild the frontend when browser settings change. The supplied development deployment is configured; production still needs its own configuration. Free-model availability and upstream limits can change.

## Product flow

Home → About you → Your offers → Generate → Review offers → Preview → Publish → Share

- Saved setup is clearly shown with a description preview, Continue setup and a confirmed Start fresh action.
- Audience, language and optional Instagram context stay visible during setup. The username becomes a clickable public profile link; Instagram is not read.
- Back and refresh preserve answers. Generation uses a centered progress dialog; failures retain the input.
- Creators can edit bio and offer fields, regenerate the whole store or one part, and restore recent versions.
- Creators select the offers they can deliver. Unselected ideas remain private, and later edits do not change the published snapshot until republished.
- The final screen explains how to put the public storefront URL into an Instagram bio.
- A separate private edit link grants owner access. Save it safely: there is no account recovery.

## Backend and API

Convex HTTP actions are exposed on **`.convex.site`**, while `.convex.cloud` is the deployment/client API URL. The app's base HTTP URL is `https://YOUR_DEPLOYMENT.convex.site/api`.

| Method | Path            | Purpose                                                                 |
| ------ | --------------- | ----------------------------------------------------------------------- |
| POST   | `/generate`     | Validates input and calls Kilo; returns a private draft and edit token. |
| POST   | `/regenerate`   | Regenerates the whole store, bio, or one product with revision checks.  |
| PATCH  | `/storefront`   | Saves private content with owner-token and revision checks.             |
| POST   | `/publish`      | Publishes selected ready offers and returns activation metadata.        |
| GET    | `/public/:slug` | Published content only, plus the supplied Instagram username.           |
| GET    | `/owner/:slug`  | Owner data; requires `x-edit-token`.                                    |
| POST   | `/track`        | Increments published page views without changing the content revision.  |

Public requests cannot directly invoke the database functions: all queries and mutations are **internal**. The HTTP boundary verifies owner tokens and returns explicit DTOs, excluding token hashes and original inputs. Tokens contain 256 random bits; only SHA-256 hashes are stored. CORS allows the configured frontend origin; it is not a substitute for token authorization.

Convex mutations make revision checks and updates atomic. Millisecond ISO revisions advance monotonically; view increments leave revisions unchanged. Quotas use transactional indexed buckets, a daily global cap, and bounded expired-bucket cleanup. Forwarded IP-based limits are a best-effort abuse signal; the global cap also protects provider usage. Token refresh, provider credentials and model calls stay server-side.

The AI layer uses scope-specific JSON schemas, Zod validation, distinct offer formats, conservative INR price heuristics and creator review. Prompts request complete sentences in plain professional language. Invalid output gets a corrective retry within an 18.5-second budget. Kilo failures never silently create generic replacement cards. Generated prices follow heuristic bands; manual prices, including zero, are preserved.

## Checks

```sh
npm run check          # formatting, frontend/backend TypeScript, tests, build
npm run test:database  # Convex function/HTTP unit tests using convex-test
```

`convex-test` and provider fixtures are used only in automated tests. The application uses the real hosted Convex database and real Kilo calls; it has no in-memory database fallback.

Live integration checks create real stores and consume model quota. Run them on a development/test deployment:

```sh
node --env-file=.env.development.local scripts/activation-check.mjs
EXPECT_SOURCE=ai node --env-file=.env.development.local scripts/live-check.mjs
```

The activation checker creates one store and exercises publishing, readiness and snapshots. The broader live checker creates ten stores and requires a temporarily higher test generation allowance. Neither prints edit tokens.

After building, run these in separate terminals to verify Cloudflare routing and security headers:

```sh
npx wrangler pages dev dist --port 8789
npm run test:pages
```

## Deploy to production

1. Create/select the production Convex deployment. Configure its server variables, including `APP_ORIGIN` set to your final Cloudflare domain.
2. Run `npm run deploy:backend` (`convex deploy`) to deploy the schema and functions to production. Development commands target the configured dev deployment instead.
3. Configure Cloudflare Pages with the **production** `VITE_CONVEX_URL`, build command `npm run build:production`, output `dist`, and Node 24. Remove local API overrides. Use separate backend deployments for interactive previews when needed.
4. For direct upload, create the Pages project, update `wrangler.toml`, put the hosted frontend settings in ignored `.env.production.local`, then run `npm run deploy` after `npx wrangler login`.
5. Test generation, editing, regeneration, publishing and a signed-out public link from the final origin on a phone. Keep the app up for at least two weeks after submission.

The build guard rejects missing, placeholder, insecure and local API URLs. Pages uses its native SPA fallback for setup, editor and public routes; do not add a top-level `404.html`. `public/_headers` supplies security headers. Hosted Convex development is connected; the production Cloudflare deployment and live PostHog delivery still need configuration and verification.

## Repository layout

- `src/`: creator onboarding, editor, public storefront and sharing UI.
- `shared/`: domain schemas, AI prompts/validation, pricing, activation and token helpers.
- `server/`: HTTP contract and repository interface.
- `convex/`: schema, internal transactional functions, HTTP routing, generated bindings and admin-only import utility.
- `tests/`: domain, AI, frontend helpers, Convex HTTP/mutations and deployment checks.
- `scripts/`: build guards, live checks and the one-time legacy migration.

## Existing data

The development migration preserves public slugs, owner-token hashes, revisions, private content and published snapshots. It does not modify the source database or overwrite existing Convex stores. `scripts/migrate-legacy-stores.mjs` is an explicit admin-only migration aid, not an application dependency. It requires the original Docker source only when rerunning the migration:

```sh
CONVEX_MIGRATION_DEPLOYMENT=bold-bandicoot-351 node scripts/migrate-legacy-stores.mjs
```
